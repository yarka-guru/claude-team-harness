# Team protocol

The lead (main session) staffs, controls and accepts the work and is the only one who talks to the user. The user watches a live dashboard of the chat, the board and who holds which file, so keep what you post true and short.

Language
- Write in English or the team's own language, whichever is natural.
- When the STE check is on (`ste` in `.claude/team/config.json` is `warn` or `deny`), messages to other agents (`ask`, `answer`, `decision`, `blocker`, `handoff`, `report`, SendMessage) and your report at the end of the task are in Simplified Technical English (STE). A `say` status line stays in English or the team's language.
- STE in short: one instruction in each sentence. Maximum 20 words in an instruction, 25 in a description. Condition first. No contractions. No semicolon. Active voice, no `-ing` verb forms, no `has done` or `is doing` forms. Simple words, one name for one item. `check` and `test` are nouns. Quoted output and code stay as they are.
- The hook examines each brief, SendMessage text and chat post (not a plain `say`) and adds an `ste:` note with the findings to your next context. Correct a hard finding in your next message. In `deny` mode a brief or SendMessage with too many hard findings is stopped. `team.py ste <file>` checks a draft before you send it.

Team chat: `python3 .claude/team/team.py say --as <handle> [--to <handle>|<role>|all] [--kind K] [--task T-n] "text"`
- One or two plain sentences, facts not chatter. The chat is internal to the team, not an outward action: read-only roles post too.
- Kinds: `say` status, `ask` you need advice or a decision, `answer`, `decision` something others must follow (API shape, file ownership, branch, naming), `blocker` you cannot proceed, `handoff` output another agent consumes, `report` your result in one or two lines.
- Post at least: a `say` with your plan when you start; a `decision` or `handoff` the moment you fix something others depend on; a `blocker` as soon as you are stuck; a `report` right before you finish.
- Your latest `say` is the line the user sees next to your name under "Who's doing what". Each time you move to a new step, post one plain sentence of what you are doing now, without ids or tool names: `say --as <handle> "I examine the notifications on a copy of the live database"`.
- When another agent owns the area, ask instead of guessing. Messages to you, your role or all arrive by themselves as `[team chat]` lines on your next tool call. Answer only with something specific; otherwise carry on.
- Asking a specific agent to do something (QA, a fix, an answer): SendMessage to them. It wakes an idle agent. A busy agent gets it on its next tool call as a `[team chat #id] … (DM …)` line and once more natively when its turn ends: that is the same message, act on it once. Never conclude a message was lost; check `team.py feed` or wait for their reply.
- Team chat (`team.py ask|answer|handoff --to <handle>`) reaches a working agent on its next tool call and does NOT wake an idle one. Before an agent stops, only an `ask`, `handoff`, `blocker` or `decision` addressed to its handle holds it back once to read; `say`, `answer` and `report` wait until it next wakes. When `team.py` warns that the target is idle or unknown, send it with SendMessage instead.
- Messages arrive in full. One too long for a single delivery ends with a `team.py read <id>` pointer; `team.py read <id>` prints any message in full. For long content (specs, QA lists), still prefer a file in your scratchpad and send the path. The scratchpad under `/tmp` gets cleaned: a script or runbook the user will run on a later day goes to `.claude/team/keep/<ticket>/`. Both channels are mirrored to the dashboard.
- When you receive a request from another agent, reply in one line that you took it ("I start the 4 QA items") before working, so they know it landed.
- Build work runs in pairs: the builder and its reviewer are named teammates and send each other handoffs and findings directly; only the final PASS/FAIL goes to the lead.
- If another agent is working next to you (see «Who else is working right now»), talk to them directly instead of routing through the lead: ask before guessing about their area, hand off results the moment they are ready, review each other's piece when it helps.

Board: `team.py task <start|review|block|wait> T-n [--note "..."]`, `team.py board`, `team.py who`
- Your card moves to review by itself when you finish; only the lead moves it to done. `block` with a note when stuck, `wait` when only the user can unblock it (an approval, a `!` command).

Conflicts
- Every Edit/Write claims the file for you until you finish. Editing a file another agent holds is denied: ask them, do not work around it.
- git checkout/switch/stash/reset/rebase/pull/clean/restore in a worktree where others have edits is denied: take your own worktree (`git worktree add`).

Fact-check gate (enforced by the hook, for every agent and the lead)
- Gated calls: Slack send/draft/schedule message and canvas create/update; Jira create (summary, description, text in additional_fields), edit (text fields), transition with a comment or text fields, comment, worklog comment; Confluence page create/update (incl. versionMessage) and footer/inline comments; `gh pr create|edit|comment|review|close|reopen|merge`, `gh issue create|edit|comment|close|reopen`, `gh release create|edit`; `gh api` writes to comments/replies/issues/pulls/releases/reviews endpoints; GraphQL mutations with text. A gated call is blocked while its text has dates, weekdays, times, numbers, versions, ticket/PR refs or cron and no PASS for that exact text in the last 24h. The denial lists the facts and saves the text to `state/factcheck/<hash>.txt`.
- gh text goes only through `--body-file`/`--notes-file <literal path>`, written in an earlier call; `$(...)`, `$VAR` paths, stdin, `--fill` and `--generate-notes` are denied. Text over 100,000 characters is denied: split it or ask the lead to waive.
- PR title flow: run `gh pr create --title "PROJ-34: ..." --body-file body.md`; when blocked, a reviewer passes the saved file the denial names (title and body together) and the same command then goes through unchanged.
- The author's step before the reviewer: next to the draft goes `<draft>.evidence.md`, one line per sentence that states a result, cause, status or scope ("passes", "answered", "recovers", "rebased on", "since") with the command or URL and the output that shows it. A sentence with no line is cut or narrowed before hand-in, and the file is redone after every code change. Most fact-check FAILs are one sentence that overstates while the numbers in it hold: "never recovers", "every model answered", "the linter passes".
- A reviewer or codex agent that did not write or edit the text checks every fact against a primary source: kubectl/API output, `gh pr view`, a Jira read, deployed values at the merged commit, a calendar computation. PR bodies, KB, tickets we wrote, drafts, agent reports and chat are derived and do not count. Recompute every date and number; do not compare one of our texts with another. The tokens are the minimum: names in backticks, procedures and "X reads Y from Z" statements are checked against the code too, never against another ticket or draft that says the same.
- Reviewers have no Write tool: `team.py factcheck tokens <file> --json` prints the template; write claims.json with a Bash heredoc, one entry per fact exactly as printed, `"source_kind": "primary"`; then `team.py factcheck pass <file> --as <own handle> --claims claims.json`. It refuses an uncovered fact, an empty or derived source, a weekday that contradicts a full date, and a first-run date that is not the schedule's first firing (name a later start in the text: "from <date>", "deploy on <date>").
- A wrong fact: `team.py factcheck fail <file> --as <own handle> --note "..."`. Only the lead waives: `team.py factcheck waive <file> --as lead --reason "..."`; every waiver is logged for the retro.
- Any edit changes the hash: check again after every change, then repeat the blocked call unchanged.

Security work (any run of an exploit or proof of concept, a local repro of a security bug included; scans, fuzzing, prompt-injection and guardrail tests, sandbox probes. Reading code for holes, reviewing a diff and writing the fix are ordinary work)
- Scope file first. The lead writes `.claude/team/keep/T-<n>/scope.md` from `.claude/team/security/scope-template.md` before staffing: who owns the target, in-scope targets, permitted actions, network boundary, out of scope, stop conditions. The brief carries it as the part `Security scope:`. No scope file, no run: ask the lead.
- The hook checks it (mode: key `security` in `.claude/team/config.json`, `off`/`warn`/`deny`, deny when absent; `TEAM_SECURITY` overrides). The part is a line `Security scope:` with the colon (list marks, quote marks, checkboxes or bold before it also count). An Agent brief with the part takes its card from the description, else the first line of the brief, else that line; a SendMessage takes it from that line, else from the sender's card; a different card id in that line is denied, and so is a text whose `Security scope:` lines name two or more card ids (one card id for each brief: send a separate brief for each card). Such a brief or SendMessage is denied unless the card is on the board and `keep/T-<n>/scope.md` is a regular file (no symlink, at most 64 KB, lines up to 1000 characters) where: `Approved by the user:` is exactly a date (YYYY-MM-DD or DD.MM.YYYY) and the user's words in quote marks («», "", “” or ''), with at most a period after them, and the words do not start with a refusal (no, nope, nah, not, not yet, pending, later, wait, hold on, ні, ще ні, поки ні, не, пізніше, потім, згодом, зачекай, don't, stop, declined and the like, also after leading punctuation: put the yes first); `Owner of the target:` is plain "the user" or "employer, local copy" (no bold), followed by nothing or by one of `. , ; : ( -` and a note; "In scope" has at least one filled item; an item `name: value` (also `=`, `—`, `–` or ` - `, bold name included) counts only when the value is filled, not empty, a `<placeholder>`, TBD, TODO, none, n/a, unknown, to be decided or only punctuation. A deny message starts with the `Security scope:` line of the text, then the reason. A brief on a card that has a scope file and no `Security scope:` part is denied (such a brief is tied to its card by the description or its first 300 characters, so the card id goes into the description); reviewer, codex, researcher, Explore and Plan runs get a note instead. The hook cannot recognise a security run on a card with no scope file: a brief with security words gets only a note, so the scope file is the lead's duty, not the hook's. Only the lead writes `scope.md`: an Edit or Write of it by another agent is denied. A Bash command is never denied here: one that names the file together with a write gets a note and a `security` event in `team.py feed` and in the dashboard chat, which the lead reads before each report, and writing the file that way breaks this protocol.
- The scope is an intent, not a description of the environment: "do not contact hosts outside <list>" holds even when a firewall is missing. Never read it as "whatever I can reach is allowed".
- Targets are only systems the scope file names. A host, account, cluster, repo or bucket you find on the way (a neighbour container, a metadata endpoint, a colleague's namespace, a third-party service) is out of scope until the lead adds it.
- Read-only first. Reading, listing and analysing are yours. Every step that changes state on a target that is not your own throwaway copy (write, delete, restart, create a user or token, send traffic that can degrade a service) is a command you hand to the lead; the user runs it.
- No autonomous attack traffic against live production. Run on a local install, a local container or Kubernetes stand or a dev replica; where only production shows the problem, stay passive and read-only.
- Fetch nothing mid-run: install tools before the start and say in the report what you would have needed. Do not open tunnels, reverse shells or listeners reachable from outside the machine.
- Stop and report at once, with a `blocker` to the lead, when: an action reached something outside the scope; a probe got further than the scope allows (an escape from a container or VM, credentials of another tenant, data of real users); a control you were told to respect turned out to be absent. Do not continue "to see how far it goes", do not clean up evidence. The lead tells the user the same hour, with the transcript path.
- The transcripts (`~/.claude/projects/**`) and the card's `keep/` folder are the evidence of a security run: do not delete them while the card is open. Security-card transcripts and scope files do not go to `codex` or any other third-party model. Findings about a hole that is still open stay out of public repos and outward text.

Shared local containers
- The container VM (Docker Desktop, colima or similar) is shared by every agent and session. Never stop, restart or reconfigure it, and never run any `prune`. Remove only the containers, images, networks and clusters you created, by exact name, after `docker ps` shows whose they are. If the VM is stopped, start it and leave it running.

Team tooling
- Team tooling (`.claude/team/`: hook.py, team.py, teamlib.py, dashboard) runs on every tool call of every agent: change a copy, test it there, and replace the live files only after the paired reviewer's PASS.
